분석 대상: `docs/PROCESS.md`, `docs/PROGRESS.md`, `docs/design/F01_IMPLEMENTATION*.md`,

## 한 줄 결론

F01(첫 실험 하나)을 "Windows에서만" 끝내는 데도 설계 REVISE 1번, 구현
REVISE 3번, 대시보드 REVISE 1번, 그리고 "진짜 버그인 줄 알았던" 진행률
진단 1번, 이렇게 총 **6번의 "만들고 → 남이 의심하고 → 실제로 뚫어보고 →
고치고 → 또 의심하는" 반복 루프**를 돌았다. 이 중 3번(구현 REVISE)은 실제로
파일이 프로젝트 밖으로 새거나 개인정보(컴퓨터 사용자 이름, 폴더 경로)가
새는 **진짜 보안 문제**를 잡아냈기 때문에 반드시 필요했던 시간이었다.
반면 초반 이름 불일치(폴더 이름 `analyzer` vs `doctori-analyzer`), NDK
설치 누락, SQLite 문법 실수 같은 것은 처음부터 더 꼼꼼히 준비했으면 건너뛸
수 있었던 시간이다. macOS는 이 컴퓨터에서 한 번도 실행하지 않았으므로
여전히 `deferred`(나중에 확인)/`unknown`(아직 모름)이고, 이 문서도 그
상태를 바꾸지 않는다.

## 왜 이렇게 오래 걸렸는지, 비유로 먼저 설명하면

Doctori는 "안드로이드 앱 버튼을 누르면 진짜 C++ 코드까지 연결되는가"를
증거로 증명하는 도구다. 이건 마치 **긴 도미노 한 줄**과 같다. Kotlin 코드
→ JNI(다리) → C++ 코드 → 빌드 도구(Gradle/CMake) → 완성된 파일(AAR) →
그 안의 기계어(ELF) → 증거 저장소(Ledger)까지, 한 칸이라도 삐끗하면
전체 증거가 거짓말이 된다. 그래서 이 프로젝트는 "한 명이 만들면 다른
사람(다른 AI 모델)이 반드시 직접 손으로 다시 확인한다"는 규칙
([Decision 0003](decisions/0003-two-model-mutual-oversight.md))을 정했다.
이 규칙 자체가 시간을 최소 2배로 만든다 — 하지만 실제로 그 두 번째
확인자가 세 번이나 "진짜 구멍"을 찾아냈기 때문에, 이 2배는 낭비가
아니라 보험료였다.

## 원인을 하나씩 뜯어보면

### A. 설계 단계 REVISE — 이름표를 서로 다르게 붙여놓은 문제

설계 1팀이 쓴 계획서는 폴더 그림에는 `analyzer/`라고 그려놓고, 실제 실행
명령에는 `:doctori-analyzer:run`이라고 썼다. 마치 **문패는 "101호"라고
붙여놓고 초대장에는 "102호로 오세요"라고 쓴 것**과 같다. 이대로 진행했으면
구현자가 그대로 따라 하다가 "그런 방(module) 없음" 오류로 막혔을 것이다.
같은 문서 안에서 "지금은 맥북이 없다"는 사실([Decision 0006](decisions/0006-windows-now-macos-deferred.md))도
빠뜨려서, "처음엔 맥북에서 실행한다"는 문장을 그대로 따르면 시작도 못 하는
상태였다. 이 두 문제는 **설계를 다시 쓸 필요 없이 문장 몇 개, 이름 하나만
맞추면 되는 문제**였다. 즉 오래 걸린 이유가 "어려운 문제"가 아니라
"꼼꼼함 부족"이었다는 뜻이다. 이건 다음 작업에서 충분히 줄일 수 있는
시간이다.

### B. ELF 주소가 항상 옛날 폴더를 가리키던 문제

첫 실행 결과 문서는 증거 파일 안에 "이 코드가 들어있는 파일은
`build/f01/blobs/sha256/...`에 있다"고 적었다. 그런데 이 주소가 **어떤
폴더에서 실행하든 항상 `build/f01`로 고정되어 있었다.** 다른 폴더
(`build/f01-audit`)에서 실행해도 증거 주소는 여전히 `build/f01`을 가리켰다.
비유하면, **이사를 갔는데 택배 주소록에는 계속 옛날 집 주소가 적혀 있는
것**과 같다. 지금은 옛집이 아직 있어서 택배가 도착하지만, 언젠가 `build/f01`
폴더를 지우면 증거가 가리키는 곳이 사라진다. 이건 실제 결함이었고, 고치는 데
`elfLocatorPath()`라는 함수를 새로 만들어 "지금 실제로 실행한 폴더"를
기준으로 주소를 계산하게 바꿔야 했다.

### C. AST 원본 파일에 컴퓨터 개인정보가 15,533번 새어나온 문제

Clang이라는 도구가 C++ 코드를 분석해서 만드는 원본 결과(`ast/raw.json`,
크기 약 3.4MB) 안에는 이 컴퓨터의 실제 사용자 계정 이름과 전체 폴더 경로가
그대로 들어있었다. 검증팀이 실제로 세어보니 **15,533번**이나 등장했다.
비유하면, **비밀 편지를 다른 사람에게 전달하는데, 편지지 뒷면에 내 집
주소와 이름이 워터마크로 잔뜩 찍혀 나오는 것**과 같다. 이 파일을 다른
사람에게 보내거나 인터넷에 올리면 개인정보가 함께 전달된다. 고치는 데는
`AstPathNormalizer`라는 정리 도구를 새로 만들어서, 프로젝트 안 경로는
`<PROJECT_ROOT>/...`로, 프로젝트 밖 경로(SDK, 헤더 파일 등)는
`<EXTERNAL_PATH>`로 바꿔치기하도록 했다. 실행할 때마다 함수 이름, 줄 번호
같은 "의미 있는 정보"는 그대로 두고 "컴퓨터 고유 주소"만 지우는 정교한
작업이라 시간이 걸렸다.

### D. junction(폴더 바로가기)으로 실제로 뚫린 문제 — 이번 작업에서 가장 심각했던 발견

`analyze`라는 명령은 실행되는 동안 스스로 `ast/`와 `blobs/sha256/`이라는
하위 폴더를 만든다. 그런데 "이 경로가 프로젝트 안인지" 확인하는 명단에
이 두 폴더가 **빠져 있었다.** 검증 2팀이 이걸 실제로 시험해봤다.

1. 프로젝트 안의 `build/.../ast` 자리에, **프로젝트 밖 임시 폴더를
   가리키는 윈도우 "폴더 바로가기"(junction)**를 미리 몰래 만들어둔다.
   (관리자 권한 없이도 만들 수 있는 방법이다.)
2. `analyze`를 정상 실행한다.
3. 결과: **오류 하나 없이 성공**. 그리고 Clang이 만든 원본 파일
   (3,498,074바이트)과 컴파일된 라이브러리 조각(`.so`에서 뽑은 바이트)이
   **진짜로 프로젝트 밖 폴더에 저장됐다.**

비유하면, **현관문은 비밀번호로 꽁꽁 잠갔는데, 부엌 뒷문에는 자물쇠를
아예 안 채워놓은 것**과 같다. 도둑(공격자)이 정문(명령줄 `--run-dir` 옵션)
으로는 못 들어오니까, 프로그램이 "자기가 알아서 만드는" 뒷문(`ast`, `blobs`
폴더)으로 몰래 들어간 셈이다. 이건 문서상의 이론적 위험이 아니라 **검증팀이
실제로 손으로 재현해서 파일이 진짜로 새어나가는 것을 눈으로 확인한 진짜
보안 구멍**이었다. `events/` 폴더만 우연히 안전했는데, 이유를 파보니
"의도적으로 막아서"가 아니라 다른 코드(`Main.kt`)의 기본값 계산 로직과
우연히 겹쳤기 때문이었다. 즉 안전한 것처럼 보이던 부분도 사실은 "운이
좋았을 뿐"이라는 게 드러난 것이다.

고치는 데는 파일을 쓰거나 폴더를 만드는 모든 코드 경로를 `PathBoundary`
안의 딱 3개 함수(`createDirectories`, `write`, `writeString`)로 강제로
모으고, 그 3개 함수 각각이 "만들기 직전"마다 검사하도록 구조를 바꿔야
했다. 검증팀은 이후 `grep`으로 "이 3개 함수 말고 다른 곳에서 파일을 직접
쓰는 코드가 있는지" 전체 코드를 다시 훑어서 없다는 것까지 확인했다.

### E. 상호 감시 구조 자체가 시간을 늘리는 방식

Codex(1팀)와 Claude Code(2팀)는 일을 반씩 나누는 게 아니라, **같은 결과를
각자 처음부터 다시 만들어서 맞는지 대조**한다([Decision 0003](decisions/0003-two-model-mutual-oversight.md)).
그래서 한 번의 "성공"마다:

- 만드는 팀이 실행하고 문서를 쓴다. (1회)
- 감시하는 팀이 **완전히 새 폴더**를 만들어 전체 테스트와 5단계 파이프라인을
  처음부터 다시 실행하고, SHA-256 해시까지 하나하나 대조한다. (또 1회)
- 둘의 결론이 다르면(REVISE) 원래 만든 팀이 고치고, 감시 팀이 또 처음부터
  다시 확인한다. (반복)

이번 F01만 해도 이 사이클이 **구현 단계에서만 3번**(B, C, D) 돌았다. 매번
"전체 테스트 재실행(`--rerun-tasks`, 캐시 안 씀)", "AAR 새로 빌드", "5단계
명령을 처음 보는 새 폴더에서 재실행", "SHA-256 값 대조"를 반복했다. 이건
느리게 만드는 구조이지만, **세 번 모두 실제 문제를 잡아냈기** 때문에
"낭비"라고 부르기는 어렵다. 오히려 한쪽이 놓친 것을 다른 쪽이 두 번이나
잡아낸 것(C, D)이 이 구조의 존재 이유를 증명한 셈이다.

### F. 매 수정 뒤 "신선한 재현" 검사 자체가 시간이 걸리는 이유

Gradle은 기본적으로 "이미 확인한 건 다시 안 한다"(캐시, `UP-TO-DATE`)는
방식으로 빠르게 동작한다. 하지만 이 프로젝트는 "정말 지금 이 코드로
다시 돌려도 같은 결과가 나오는가"를 확인해야 하므로, 캐시를 일부러 끄는
`--rerun-tasks` 옵션을 계속 써야 했다. 게다가 "같은 폴더에서 다시 실행하면
당연히 같은 값이 나온다"는 약한 증거로 만족하지 않고, **매번 완전히 새
이름의 폴더**(`build/f01-audit`, `build/f01-fix`, `build/f01-team2-fix-audit`,
`build/f01-boundary-fix`, `build/f01-junction-fix` 등)를 만들어 "0에서부터
다시 만들어도 바이트까지 같은가"를 확인했다. 이건 마치 **같은 요리를 다른
냄비에, 처음부터 다시 만들어서 맛이 완전히 같은지 확인하는 것**과 같다.
느리지만, 이렇게 해야 "우연히 한 번 맞았다"가 아니라 "몇 번을 다시 해도
똑같다(재현성)"는 걸 증명할 수 있다. 이건 F01처럼 "증거"를 파는 도구에서는
생략하면 안 되는 시간이다.

### G. 문서·대시보드 동기화도 매번 따라붙는 작업

코드를 한 번 고칠 때마다 다음을 같이 갱신해야 했다.

- `docs/PROCESS.md`, `docs/PROGRESS.md`의 "지금 상태" 서술
- `dashboard/process.json`의 팀/마일스톤 상태와 `updatedAt` 시각
- 검증 보고서 안에 남아있던 실제 컴퓨터 사용자 이름·절대경로 6개 문서 정리
  (`docs/PROCESS.md`, `DASHBOARD_LIVE_SERVER_DEPLOY.md`,
  `DASHBOARD_V3_VISUAL_REVIEW.md`, `DASHBOARD_VISUAL_REVIEW.md`,
  `F01_IMPLEMENTATION_TEAM2_AUDIT.md`, `VALIDATION_TEAM2_DASHBOARD.md`)

이 중 문서 6곳 정리는 **처음 만들 때 절대경로를 안 쓰기로 규칙을
정해뒀다면** 나중에 따로 찾아서 지우는 시간이 필요 없었을 부분이다.

### H. 운영 오버헤드 — 실제로 버그가 아니었던 확인, 사소한 화면 문제

- **70% 진행률 진단**: 사용자가 "화면이 70%에서 안 움직인다"고 느껴서
  캐시 문제, HTTP 폴링 정지, 애니메이션 멈춤, 서버 문제까지 4개 가설을
  각각 재현해서 하나씩 배제했다. 결론은 "버그 아님, 사람이
  `process.json`에 직접 적어둔 숫자 `70`이 안 바뀐 것뿐"이었다. 실제
  코드는 정상이었지만, "확인하지 않은 걸 정상이라고 말하지 않는다"는
  원칙 때문에 4가지 가설을 다 없애는 데 시간을 썼다. 결과가 "정상"이라는
  것도 가치가 있지만, 애초에 "이 숫자는 사람이 직접 넣는 값"이라는 걸
  화면이나 문서에 더 눈에 띄게 적어뒀다면 이 진단 전체가 필요 없었을
  수도 있다.
- **대시보드 571px 잘림**: 화면 폭을 좁혔을 때 "검증팀 (Team 1)"과
  "(Team 2)"가 둘 다 "검증팀 (Tea…)"로 잘려서 구별이 안 되는, CSS 문제
  하나 때문에 REVISE 판정이 났다. 기능적으로 위험한 문제는 아니었지만,
  같은 "REVISE → 수정 → 재확인" 절차를 거쳤다.
- **초기 구현 실수 3종**: NDK가 실제로 설치 안 되어 있던 것, SQLite의
  WAL(Write-Ahead-Logging) 모드를 트랜잭션 안에서 켜려다 난 오류, 여러
  SQL 문장을 한 번에 실행하려다 난 오류. 이 세 개는 안전 설계와 무관한
  **평범한 프로그래밍 실수**였고, 고치는 자체는 오래 안 걸렸지만
  "구현 시작 → 첫 성공"까지 왕복이 3번 더 늘어난 원인이다.

## 필요했던 시간 vs 불필요하게 늘어난 시간

| 구분 | 내용 | 판단 |
| --- | --- | --- |
| **꼭 필요** | 상호 감시로 찾아낸 3개의 진짜 결함(B: 고정 경로, C: 절대경로 15,533건 누출, D: junction으로 실제 파일 탈출) | 실제 재현된 위험이라 시간을 들여서라도 잡아야 했다 |
| **꼭 필요** | 매 수정 뒤 새 폴더에서 캐시 없이 처음부터 재현하고 SHA-256까지 대조 | "우연히 맞았다"와 "항상 맞는다"를 구별하는 유일한 방법 |
| **꼭 필요** | macOS를 아직 `deferred/unknown`으로 유지하고 "통과했다"고 안 쓴 것 | 실행하지 않은 걸 확인했다고 말하면 나중에 더 큰 문제가 됨 |
| 줄일 수 있었음 | 설계 단계 이름 불일치(`analyzer` vs `doctori-analyzer`), Decision 0006 인용 누락 | 설계 문서 작성 시 자동 검사(같은 이름을 grep으로 대조)로 미리 잡을 수 있는 종류 |
| 줄일 수 있었음 | NDK 미설치, SQLite 문법 오류 | 구현 착수 전 체크리스트로 예방 가능 |
| 줄일 수 있었음 | 문서 6곳에 흩어진 절대경로를 나중에 찾아 지운 것 | 처음부터 "문서에 실제 경로 쓰지 않기" 규칙을 강제했다면 생략 가능 |
| 줄일 수 있었음(부분) | 70% 진행률 진단 전체 | 코드는 정상이었으므로, 화면에 "이 숫자는 자동 계산이 아니라 수동 입력"이라는 표시를 더 눈에 띄게 했으면 진단 자체가 필요 없었을 가능성 |

## 다음 작업부터 시간을 줄이는 구체적 방법

1. **설계 문서를 감사팀에 넘기기 전에, 작성팀 스스로 "이름 일치 자동
   검사"를 한 번 돌린다.** 폴더 이름, 모듈 경로, 문서에 적은 결정 번호
   (`grep -n "0006"` 같은)를 코드/명령과 대조하는 짧은 체크리스트만
   있어도 A 같은 REVISE 사이클 하나를 통째로 줄일 수 있다.
2. **"파일을 쓰거나 폴더를 만드는 코드는 반드시 안전 검사 함수 하나만
   거친다"는 규칙을 설계 단계부터 강제한다.** D 문제가 생긴 이유는
   "빠짐없이 다 검사했다고 믿었지만 실제로는 새로 생긴 폴더 하나를
   빠뜨렸기" 때문이다. 처음부터 `Files.write`/`Files.createDirectories`를
   코드 어디서도 직접 못 부르게 하고 공용 함수만 쓰게 했다면, 나중에
   "빠진 곳 없는지 전체 코드를 다시 훑는" 시간이 줄었을 것이다.
3. **AST 원본처럼 외부 도구(Clang)가 만드는 파일에 개인정보가 섞일 수
   있다는 걸 처음부터 가정하고, 경로 정리 단계를 설계에 포함한다.** C
   문제처럼 "나중에 발견해서 만드는" 게 아니라 "처음부터 있는 기능"으로
   만들면 재작업이 없다.
4. **문서에 실제 컴퓨터 경로·사용자 이름을 쓰지 않는 규칙을 커밋 전
   자동 검사(간단한 `grep "C:\\Users"` 같은 스크립트)로 강제한다.** 사람이
   나중에 6개 문서를 손으로 찾아다니는 대신, 커밋하기 전에 자동으로
   걸러지면 이 시간을 아예 없앨 수 있다.
5. **재확인 범위를 명확히 좁힌다.** 이미 이번 작업의 마지막 재감사
   (`F01_JUNCTION_TEAM2_REAUDIT.md`)에서 "코드 읽기 + 테스트 재실행 +
   문제였던 부분만 새로 재현하면, 안 바뀐 부분(예: AAR 전체 재빌드)까지
   반복할 필요는 없다"는 판단을 했다. 이 판단 기준(무엇을 재확인하고
   무엇은 건너뛰어도 되는지)을 다음 작업부터는 처음부터 문서로 정해두면,
   매번 "이번엔 어디까지 다시 해야 하나"를 판단하는 시간이 줄어든다.
6. **"이 숫자는 사람이 직접 넣는 값"처럼, 자동 계산이 아닌 수동 값은
   화면이나 문서에 눈에 띄게 표시한다.** 70% 진단처럼 "버그가 아닌데
   버그처럼 보이는" 상황 자체를 줄일 수 있다.

## macOS 상태 (변경 없음)

이 문서를 쓰는 지금까지 macOS arm64/Intel에서 F01을 실행한 기록은
없다. Windows current gate의 **APPROVE**는 Windows에만 적용되며, macOS는
계속 `status=deferred`, `confidence=unknown`이다. 회사 MacBook이나 macOS
CI를 확보한 뒤에만 macOS 게이트를 별도로 실행하고 판정한다
([Decision 0006](decisions/0006-windows-now-macos-deferred.md)).
